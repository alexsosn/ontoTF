# I-033E5 — single-agent adversarial batch review without false independent identities

**Issue:** #325 and #303; correct earlier false premise that a separate reviewer exists.
**Base:** `bc9f24881ab9409f512fb533792e180ae7fe7b07`.

## Observations from real repository code

- Current `external_review_gate.evaluate_review_snapshot` requires GitHub `APPROVED`, a `User` distinct from PR author, and write/maintain/admin collaborator permission; it rejects author `COMMENTED` reviews. PR #324 consequently passed source-bound packet verification but the protected live workflow correctly rejected the missing external review.
- In this repository, **the development agent conducts authoring and logically independent adversarial review passes, using one GitHub account (`alexsosn`) for the audit trail**. A second identity must not be invented and the work must not deadlock on an unavailable human or App. GitHub prevents PR authors from approving their own PR; a PR review of type `COMMENTED` is possible and produces GitHub-authored immutable review ID, submitted timestamp and `commit_id`.
- Existing `pull_request_target` / `issue_comment` protected workflow executes `main` code, fetches candidate ledger, packet and source evidence **only as JSON** at exact PR SHA, and re-fetches reviews, permissions, PR identity and revision before publishing. `overlay_handoff` accepts only the exact existing observation fields and >=10 accepted decisions; preserving the current schema avoids independent refactors.
- Existing `ontoTF-batch-review-v1` row decisions and `reviewer_handoff.render_review_body` are reusable: one v1 `COMMENTED` author review can record explicit decisions, but **alone is never sufficient** to publish.

## Trust-mode architecture

Explicit opt-in label `ontology-single-agent-review` in addition to `ontology-batch-review`; default without it remains **unchanged external mode**. An author with repo permission admin/maintain/write publishes two **separate, chronological, authenticated PR-review events** at exact current head SHA:

1. Earlier `COMMENTED` review with `ontoTF-adversarial-review-v1\n` JSON object containing packet digest, nonempty *independent skeptical summary*, and all 10–50 per-row `mapping_id`, `decision_digest`, `challenge`, `source_check`. Each per-row challenge must be specific, nontrivial and not copied verbatim from proposal rationale. The source check documents checked original pinned source and a counterargument or uncertainty. This is **audit evidence**, NOT automatically a scholarly truth guarantee.
2. Later `COMMENTED` review by same GitHub author with existing `ontoTF-batch-review-v1\n` explicit `accept|reject|needs-evidence` dispositions and all row digests (can be generated by the vetted #326 handoff CLI, which never chooses dispositions).
3. Protected main reads both actual GitHub reviews, verifies distinct review IDs, chronological order, same author account and exact SHA, frozen packet and row digests, role, no stale or later author review, and the live opt-in label. No forged PR JSON, local receipt, or author-authored `approved=true` is sufficient. Output `provenance` explicitly says **single-agent**; legacy `reviewer_login` and `review_id` identify decision author and actual review event but are NOT external/independent-person approval.
4. Protected signing still requires **separate** `ontology-batch-publish` label and fresh recheck before accepted-only handoff. Existing (>=10) accepted count remains intact; skeptical decisions of reject/needs-evidence remain excluded.

This is **process-level logical independence**, not distinct reviewer identity: the agent must do a challenge-first pass, commit findings as one GitHub review, then make separate decisions as another event. The code can enforce sequencing, constraints and recorded evidence, but **cannot prove subjective cognitive independence or semantic truth**. Keep original independent-external pathway available without weakening it.

## Security and operational alternatives

- Do not change GitHub review `APPROVED` semantics, invent a fake reviewer account, falsely claim external signed approval or trust a PR-head workflow with tokens.
- Do not accept a single author comment, one self-supplied JSON receipt, blank boilerplate source checks or an unconditional `accept` list. Strict event headers, per-row commitments, and current SHA are mandatory.
- A malicious author with protected repo admin privileges can still publish poorly reasoned mappings; the aim here is honest, auditable, adversarial single-agent review plus tests and preserved original corpus pins, not proof of a second trust principal.
- No new per-entity PR, CLI workflow, or 10× CI tax.
