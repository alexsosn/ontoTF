# Mapping progress dashboard

This page is a static report generated from the same authoritative XML files that the development package reads. It neither changes mappings nor ships corpus text.

## Build and preview

From the repository root with Python 3.12 or newer:

```sh
python -m pip install -e .
python -m unittest tests.mapping_catalog.test_progress_tracker tests.mapping_catalog.test_scoped_progress -v
python -m scripts.pages.build_progress --out /tmp/ontotf-pages
python -m http.server 8000 --directory /tmp/ontotf-pages
```

Open http://localhost:8000. The output contains only `index.html` and `progress.json`; no API credentials, JavaScript, or external runtime dependencies are required. The source commit is shown on the page. Detailed evidence, inventory paths, declaration counts and the historical work queue remain in the downloadable JSON or repository.

## Dashboard design

The landing page answers three questions: how much of the measured categorical
annotation is mapped, how much of the researched scope each ontology covers,
and where further research or mapping is needed. Category coverage gives each
observed value equal weight; annotation coverage weights by corpus frequency.
The ontology grid uses partial applicability denominators only; no universal
completion score is shown. Corpus details expose structural coverage, separate
classification rates for each unit kind and ranked unreviewed domains.
The snapshot cannot support a time series until comparable prior snapshots exist.

The design follows [UK Analysis Function dashboard guidance](https://analysisfunction.civilservice.gov.uk/policy-store/data-visualisation-building-and-managing-dashboards/),
[NHS Turas dashboard guidance](https://www.turasdesignsystem.nhs.scot/design/data-visualisation/data-dashboards/designing-a-dashboard/)
and [Tableau visual practices](https://help.tableau.com/current/blueprint/en-us/bp_visual_best_practices.htm).
Use fixed 0–100% bars, text labels alongside color, responsive layouts and
progressive disclosure. Do not promote declaration counts or raw file links
to headline metrics. Preserve missing, empty and zero states independently.

## Accounting

- A reviewed category selector (excluding individual entity-kind declarations) is a distinct (corpus, corpus version, kind, node, feature, value, from, to) key. Multiple target IRIs do not multiply this count. Exact takes precedence over qualified; ambiguous candidates, native-only and unsupported are not positive.
- An ontology column counts distinct positive selectors and distinct schema items. A selector may belong to multiple ontology columns; the unique-positive total is a union. Unrecognized namespaces are grouped as Other.
- A schema item is a node type, node feature or edge feature, counted once by name and kind. Mapping one feature value counts as touching the feature, not as completing its entire value domain. A node mapping's surface-feature guard is not a mapping of the feature itself. Entity-kind links are not schema mappings.
- Schema inventories use existing pinned R-005 censuses, the Pseudepigrapha I-017 census, and the [pinned current ORACC/TLHdig schema snapshots](../../docs/research/data/pages-current-schema-snapshots.json) extracted from the upstream generated feature/type references. TLHdig's optional unloaded provenance features are excluded; TF warp/configuration names are excluded. Other native or technical features remain in the denominator.
- A missing, version-mismatched, or explicitly revision-mismatched inventory produces no schema rate; selector counts still appear. The combined schema rate uses only comparable corpora, explicitly labeled. Version strings alone do not authenticate corpus bytes.
- The historical pooled value lists are retained as a secondary comparison for previously mapped feature families only. Values are pooled across native scopes; this is neither full node-scoped coverage nor a claim that every observed value is semantic. Missing/truncated domain lists are not extrapolated. The JSON includes unreviewed and outside-inventory values and per-ontology intersections.
- Current scoped evidence: nine actual pinned TF inventories under `docs/research/data/generated/scoped/`, generated by the existing R-005 workflow (run [45816402169](https://github.com/alexsosn/ontoTF/actions/runs/45816402169)). Compare repository, catalog version and explicit source pin; the ORACC release ID and internal TF version are separate. Compute unconditional node types, whole scoped features, scoped categorical values, actual directed edge pairs and selected edge values independently. Guarded node categories report their observed guard-bearing node counts separately, even if the guard happens to cover every node. A generic feature or edge mapping applies to the actual observed scopes or endpoint pairs of that named feature, not to its individual values; explicit scope/direction constrains that projection. An XML edge mapping with a value accounts only for that observed edge category, never its whole feature. The XML loader remains authoritative for runtime queries; these statistics are not a new inference API.
- The initial [applicability policy](../../docs/research/data/scoped-applicability.json) specifies source-reviewed families for ontology assessment, by corpus/revision and native granularity. These are partial review domains, not guaranteed ontology matches or exhaustive semantic eligibility. A positive result in one ontology cannot satisfy another. Global native-only/unsupported and ambiguity are reported separately from ontology-specific decisions. Unclassified families stay visible; unknown scope is never zero. The policy may explicitly exclude a native unit from the current mapping granularity (e.g. a source digest, compatibility alias, or an individual spelling already represented at feature granularity). Excluded and unclassified units are counted separately for each item kind; an excluded item cannot simultaneously be routed. Reasons and source evidence are shown with corpus details. No global ontology completion percentage is asserted. The JSON includes classification counts per observed kind and unreviewed item identities. Value-weighted coverage counts feature annotations, not unique token coverage.
- The historical P-004 routed inventory is retained in the JSON, preserving its original seven-corpus and grouped ontology counts. It cannot be divided into the current node-scoped selector counts. The historical denominator is not substituted for the current scoped evidence or partial ontology review scope.

New mapping rows and corpus XML files appear automatically. An additional corpus inventory is optional; when absent the schema denominator remains unknown until source evidence is available. If upstream versions change, refresh the corresponding source inventory, not a manually maintained progress total.

## Pages deployment

The [Pages workflow](../../.github/workflows/pages-progress.yml) builds on relevant changes to main and on tracker PRs; only main can deploy. PR artifacts can be downloaded from Actions to preview the generated page. Enable **Settings → Pages → Build and deployment → Source: GitHub Actions** once if it is not already enabled. This repository's intended URL is https://alexsosn.github.io/ontoTF/. The workflow does not modify repository settings, publish a package, or commit generated reports.

The page should show the exact source commit used by the build. If the deployment fails, inspect the Pages workflow; a successful build artifact does not prove that the public site is live.
